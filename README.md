# RoboGuard Reproduction with SPINE Integration


A reproduction and extension of **RoboGuard: Safety Guardrail for LLM-Enabled Robots**, with **Google Gemini 2.5 Pro** and **SPINE** integration.


This repository contains the reproduced RoboGuard safety-guardrail pipeline together with:


- OpenAI-based RoboGuard contextual grounding
- Google Gemini 2.5 Pro integration
- SPOT-based formal safety verification
- SPINE semantic planning integration
- Gemini-enabled SPINE planning


The primary goal of the SPINE integration is to evaluate whether candidate plans generated by an LLM-enabled planner can be validated by the RoboGuard safety guardrail.


---


## 1. Project Overview


RoboGuard provides a safety guardrail for LLM-enabled robots by converting natural-language safety rules and a semantic scene graph into formal **Linear Temporal Logic (LTL)** constraints.


SPINE is an LLM-enabled planner designed for missions with incomplete natural-language specifications in unstructured environments.


In this repository, SPINE is integrated with RoboGuard so that:


1. SPINE receives a robot task and a semantic scene graph.
2. SPINE generates a candidate robot action plan.
3. RoboGuard generates formal safety constraints from safety rules and the scene graph.
4. The candidate SPINE plan is passed to RoboGuard's formal safety verifier.
5. The plan is classified as **SAFE** or **UNSAFE**.


The integrated architecture is:


```text
                 Task
                  │
                  ▼
         ┌─────────────────┐
         │      SPINE      │
         │ Semantic Planner │
         └────────┬────────┘
                  │
                  ▼
          Candidate Plan
                  │
                  │
                  ▼
Safety Rules ──► RoboGuard
                  │
                  ▼
         Contextual Grounding
         (OpenAI / Gemini)
                  │
                  ▼
            LTL Constraints
                  │
                  ▼
           ControlSynthesis
                  │
                  ▼
            Spot / Büchi
                  │
                  ▼
         Candidate Plan Check
                  │
             ┌────┴────┐
             ▼         ▼
           SAFE      UNSAFE
```


## 2. Relationship Between RoboGuard and SPINE
RoboGuard and SPINE are separate research projects and papers.
This repository does not replace the original SPINE implementation.
Instead, the repository uses the SPINE planning framework as the candidate-plan generator and connects its output to the RoboGuard safety-verification pipeline.
Conceptually:
```text
SPINE
 │
 │ generates
 ▼
Candidate Robot Plan
 │
 │ evaluated by
 ▼
RoboGuard
 │
 ├── Contextual Grounding
 │
 ├── LTL Safety Specifications
 │
 ├── ControlSynthesis
 │
 └── Spot
       │
       ▼
  SAFE / UNSAFE
The integration therefore, allows the planner and safety guardrail to remain conceptually separate:
      Planning Layer
             │
             ▼
           SPINE
             │
             ▼
      Candidate Action Plan
             │
             ▼
       Safety Layer
             │
             ▼
         RoboGuard
```

## 4. RoboGuard Safety Pipeline


The core RoboGuard architecture remains:
Safety Rules + Scene Graph
           │
           ▼
     Contextual Grounding
      (OpenAI / Gemini)
           │
           ▼
       LTL Constraints
           │
           ▼
     ControlSynthesis
           │
           ▼
     Spot / Büchi Automaton
           │
           ▼
     Candidate Action Plan
           │
           ▼
     Safety Validation
           │
           ▼
       SAFE / UNSAFE


### 4.1 Contextual Grounding
The contextual-grounding module generates LTL safety specifications from natural-language rules and the current semantic scene graph.
The implementation is located at:
src/roboguard/generator.py
The contextual-grounding component can use:
OpenAI
Google Gemini 2.5 Pro
The generated response contains the conceptual structure:
RULE
├── constraint
└── reasoning
For example:
G(!goto(construction_area_1))
means that the robot must always avoid the specified region.


### 4.2 Robot Action API
The action abstraction is defined in:
src/roboguard/prompts/api.py
The available actions include:
goto(region)
map_region(region)
explore_region(region, radius)
extend_map(x, y)
inspect(object, query)
replan
answer(answer)
clarify(question)
These actions provide the interface between the generated safety specifications and candidate robot plans.


### 4.3 LTL Safety Synthesis
The formal verification component is implemented in:
src/roboguard/synthesis.py
The ControlSynthesis class:
Receives generated LTL constraints.
Converts the constraints into a Spot-compatible representation.
Generates a Büchi automaton.
Converts candidate actions into formal propositions.
Traverses the automaton.
Determines whether the candidate action sequence satisfies the safety constraints.
The result contains the safety status of the candidate action sequence.

## 6. Gemini-Enabled SPINE
GeminiSPINE is implemented by extending the original SPINE planner.
The goal is to replace the OpenAI LLM backend while retaining the existing SPINE mechanisms for:

JSON parsing

retry logic
feedback handling
action extraction
The Gemini implementation is located at:
spine/gemini_spine.py
The corresponding test is:
spine/test_gemini_spine.py
This allows Gemini to generate candidate SPINE plans while maintaining compatibility with the existing SPINE planner interface.


## 7. SPINE Scene Graph
The SPINE planner uses a semantic scene graph represented by the GraphHandler class.
The scene graph used in the RoboGuard integration is:
data/perch_small.json
The graph is initialized using the same structure used by the RoboGuard evaluation code.
For example:
handler = GraphHandler("")


success = handler.reset(
   str(working_graph).replace("'", '"'),
   init_location,
)
The resulting graph is then provided to SPINE.


## 8. Candidate Plan Generation
A task is provided to SPINE together with the current semantic scene graph.
For example:
Task:
Inspect the plan.
SPINE produces a structured response containing fields such as:
primary_goal
relevant_graph
reasoning
plan
A candidate plan may have the form:
goto(ground_6)
explore_region(ground_6, 3.0)
replan()
The plan is then available to RoboGuard for safety validation.


## 9. SPINE + RoboGuard Evaluation
The main purpose of the integration is to evaluate candidate plans generated by SPINE using RoboGuard.
The combined evaluation pipeline is:
           Scene Graph
                 │
                 ▼
              SPINE
                 │
                 ▼
         Candidate Action Plan
                 │
                 │
                 ▼
       ┌─────────────────────┐
       │      RoboGuard      │
       │                     │
       │ Contextual Grounding│
       │        ↓            │
       │  LTL Constraints    │
       │        ↓            │
       │ ControlSynthesis    │
       │        ↓            │
       │      Spot           │
       └──────────┬──────────┘
                  │
                  ▼
            SAFE / UNSAFE
This separates planning from formal safety verification.
SPINE proposes what the robot should do.
RoboGuard determines whether the proposed action sequence satisfies the safety constraints.


## 10. Important Action Abstraction
The execution API and formal LTL abstraction are not necessarily identical.
In particular, the execution API may represent inspection as:
inspect(object_node, vlm_query)
while the current formal LTL abstraction uses:
inspect(object_node)
Therefore a safety constraint should use:
G(!inspect(knife_1))
and not:
G(!inspect(knife_1, "*"))
or:
G(!inspect(knife_1, "query"))
The Gemini-specific safety prompt explicitly instructs the model to follow the formal action abstraction.
This ensures that generated LTL specifications remain compatible with the formal verification component.

## 15. Testing the Gemini-SPINE Integration
The Gemini-SPINE integration can be tested independently before connecting it to the full RoboGuard evaluation.
From the repository root:
cd spine
python test_gemini_spine.py
The test:
Loads data/perch_small.json.
Initializes the SPINE GraphHandler.
Creates a GeminiSPINE planner.
Sends a task to Gemini.
Parses the response using the existing SPINE planning logic.
Prints the resulting candidate plan.
A successful execution should produce output similar to:
Graph reset: True
Current location: ground_1
Number of graph nodes: 25


Calling Gemini-SPINE...


Gemini-SPINE success: True


--- GEMINI-SPINE RESPONSE ---
...


--- CANDIDATE PLAN ---
goto(...)
explore_region(...)
replan(...)
The exact plan depends on the LLM response.

## 19. Current Scope
The current 0.3.0 implementation focuses on integrating the SPINE planning component with RoboGuard's safety-verification pipeline.
The immediate experimental objective is:
SPINE-generated candidate plan
            ↓
      RoboGuard guardrail
            ↓
      Formal verification
            ↓
       SAFE / UNSAFE
Full SPINE functionality, including its ROS-based Clearpath Jackal deployment and complete exploration framework, remains outside the scope of this integration.
